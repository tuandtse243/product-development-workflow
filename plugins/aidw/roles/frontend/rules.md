Each rule is answered pass or fail on the diff of one task. A rule binds when its "applies when" holds; the reviewer
cites the id in a finding (`1. F4: components/booking/SlotList.tsx: ...`). A rule whose right action is to ask is kept
when you asked (a Consultation, see "Ask before you guess"); guessing breaks it. A script named in a rule is your
measuring tool (`aidw plugin-path roles/frontend/scripts/<name>.mjs`): its output is a worklist, never the proof.

| id | rule | applies when | checked by |
|---|---|---|---|
| F1 | Every request field, response field, status and error type the client sends or handles is one the brief's contract names; for a case the contract does not cover (an error with no body, a field the screen needs), ask `api-designer`, do not guess it or compute it in the client. | the task calls an API | reviewer |
| F2 | Every color, font, font size, spacing, radius, shadow and z-layer in the diff is a token or derived from one (`color-mix`, `calc` on a token), and each token is applied where its **Use** says; for a state or element the design does not cover, ask `ui-ux-designer` as a Consultation and build the rest of the task meanwhile, never a value or a token of your own (`token-literals` lists the literals); when no Consultation is left, build with what exists and name the hole under `Owed` in the report. | the task adds or changes styles and the approved design has tokens | CLI, script, reviewer |
| F3 | Every view that reads data renders the loading, empty, error and success states the scenarios imply; the error state says what failed and offers the way out (retry, back), is announced (`role="alert"` or a live region), and is never the empty state; each named state has a test. | the task adds or changes a view that reads data | reviewer |
| F4 | Every interactive element is a native control (`button`, `a href`, `input`, `select`, `textarea`) or has a role, a tab stop and keyboard handling; each has an accessible name a person can read (not an icon key or a file name); each form field has a programmatic label; each meaningful image has `alt` and a decorative one `alt=""` (`a11y-names` lists candidates). | the diff adds or changes markup | script, reviewer |
| F5 | A dialog, menu, popover or drawer moves focus in when it opens, keeps Tab inside while modal, closes on Escape and returns focus to the control that opened it, and a test asserts the focus moves; no focus outline is removed without a visible `:focus-visible` replacement (`a11y-names` flags removed outlines). | the diff adds or changes an overlay or removes a focus outline | script, reviewer |
| F6 | A scenario whose WHEN is a user action is proven by a test that renders the component, finds the control by role, label or visible text and performs the action with user events; the test asserts what the user sees, never component state, instance methods, class names or a mocked child. | a scenario's WHEN is a click, tap, typing, a selection or opening something | reviewer |
| F7 | Independent reads start together (or stream behind their own boundary); a read the framework can do on the server or in a loader is not done in a mount effect; a client read that can be superseded (search, filter, tab, paging) is cancelled or ignored when superseded, so a stale response never replaces a newer one (`fetch-waterfalls` lists effects that fetch with no cancel, and awaits that could run together). | the task reads data | script, reviewer |
| F8 | A value computable from props, state or server data is computed during render, not copied into state by an effect; server data is held in one place (the framework's loader or the project's query cache), not also in a component or a global store (`fetch-waterfalls` lists effects that only copy a value into state). | the task adds client state or an effect | script, reviewer |
| F9 | A form's client checks mirror the contract's constraints (required, length, format, allowed values) and never replace the server's; each server field error is shown next to its field and tied to it (`aria-invalid`, `aria-describedby`), typed values survive a failed submit, and the submit cannot send twice while a request is pending; tests cover one client refusal, one server field error and the double submit. | the task adds or changes a form | reviewer |
| F10 | Client code reads only environment variables with the framework's public prefix (`NEXT_PUBLIC_`, `VITE_`, `PUBLIC_`, `runtimeConfig.public`), no name that looks secret (`KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `PRIVATE`) carries a public prefix, and no server-only module is imported into a client file; a call that needs a secret goes through the server (`public-env-scan` lists the reads and imports). | the diff reads an environment variable or imports across the client/server line | script, CLI, reviewer |
| F11 | A route or control the spec restricts is hidden or redirected on the client only as a convenience: the data behind it comes from an API that checks access, the decision is never taken from a value the client stores unverified (a role in `localStorage`, a query flag), and when the API does not say it checks access, ask `api-designer` and name the gap under `Found` (`route-guard-inventory` lists each route with the guard it has, if any). | the task adds or changes a route, page or control restricted to some users | script, reviewer |
| F12 | Dates, times, numbers and money are formatted with `Intl` or the project's formatter in the user's locale, never by string building; when the project has an i18n setup, every user-visible string the diff adds goes through it. | the diff shows a date, number or money value, or adds visible text in a project with i18n | reviewer |
| F13 | Every image has its dimensions or aspect ratio and a below-the-fold image loads lazily; content that arrives later reserves its space (no layout shift); a component the first screen does not need (editor, chart, map, lightbox) is loaded on demand. | the diff adds images, late content or a heavy component | reviewer |
| F14 | Client code holds no business rule the server must enforce (price, permission, limit, status transition): it shows what the API returns, and for a value the screen needs that the API does not give, ask `api-designer`, do not compute it. | the task shows or changes data the server owns | reviewer |
| F15 | The screens the task changes work at the `ui-ux` layer's three viewports and in each theme the tokens define, and the task saves fresh screenshots of the changed states into the brief's folder (the checkpoint counts them). | the task changes a screen and the approved design has tokens | CLI, reviewer |
